### 1. fn 和 fn() 有什么区别？为什么 decorator 能接收一个函数？
```
区别：
    fn 是函数对象本身
    fn() 是调用它并拿到返回值
decorator 能接收函数是因为：函数是对象，可以作为参数传递。decorator 本质就是一个“接收函数、返回函数”的函数。
```

### 2. 用自己的话解释 @log_call 与 hello = log_call(hello) 的关系。
```
它们是完全等价的，@log_call只是语法糖。
```

### 3. wrapper 为什么必须 return fn(...)？如果只调用不 return 会发生什么？
```
fn(...) 的返回值是原函数的结果，wrapper必须把它透传给调用方。
如果不return的话，wrapper就会出现所谓的吞返回值的问题。
```

### 4. functools.wraps 解决什么问题？至少举两个被保留的元数据。
```
解决“装饰后原函数的无信息丢失”的问题。
wraps的作用是复制被包装者的元信息，避免其丢失。
被保留的元数据：__name__、__doc__、__annotations__、__module__、__qualname__
```

### 5. 普通函数 return list 与 generator yield 在执行时机和内存行为上有什么区别
```
普通函数：立即执行，返回完整列表，数据量大时内存占用严重。
Generator：惰性执行，按需产出，内存占用很小。
```

### 6. 为什么 generator 经常被称为“一次性消费”？你如何证明这一点？
```
因为 generator 内部只有一个“当前位置指针”，遍历完就没了，不能重置。
其内部维护“当前位置”，一旦跑到末尾，状态变成 GEN_CLOSED，不能再从头开始。
再次遍历，就会发现是空的。
```

### 7. 如果要处理 5 GB 文档，为什么 generator pipeline 比先生成全部 chunk list 更值得考虑？它有没有缺点？
```
generator 优点：
    1. 节省内存
    2. 可以立即开始产出
    3. 可随时中断
    4. 对大数据友好

generator 缺点：
    1. 一次性消费
    2. 不能随机访问
    3. 不能获取长度
    4. 调试困难
    5. 异常处理复杂
    6. 不能多线程共享

generator的缺点基本就是list的优点
```

### 8. pytest fixture 与 Day 1 的全局 payload 有什么差别/优势？
```
Day1的全局payload问题在于：
    1. 其是全局可变对象，容易互相污染
    2. 无法自动清理
    3. 无法按需构造不同版本
    4. 无法参数化
pytest fixture的优势：
    1. 隔离性，每次都重新创建
    2. 生命周期可控，有function/module/session这几个级别
    3. 依赖注入
    4. 参数化
```

### 9. 什么场景适合 @pytest.mark.parametrize，什么场景不应该硬参数化
```
适合：同一逻辑的多种输入
不适合：多个不同逻辑
```

### 10. 你的 ChunkRule 为什么这样设计？如果只返回 bool，未来 Agent 审核为什么可能不够？
```
纯过滤的话bool够用了，但是Agent审核需要结构化的数据才能支撑。
bool的局限：
    1. 只能知道是否检测通过
    2. 不知道为什么失败
    3. 不知道具体是哪里失败
    4. 没有可扩展性，后续加需求会很困难
```
